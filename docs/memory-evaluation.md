# 记忆与上下文场景验证

在 DSH 0.2.2-rc.3、WSL2、Linux Node 24.21.0 的隔离 web profile 验证。
2026-11-17 验证新的模型写入核对与延迟整理，并以真实应用开发任务检查续接与事实修订；
2026-11-14 的 60 轮测试验证既有事实
版本和完整上下文选择，不当作新整理机制的长程测试。真实调用固定为 Qoder 的 dfmodel（宿主路由
[dsh-provider-qoder/dfmodel](https://github.com/mo-n/dsh-provider-qoder)）。
使用虚构事实与独立实例，不读用户真实聊天。原始会话、失败记录和证据文件仅留本机，
入库截图只含经审的合成展示内容。

## 模型写入与整理：2026-11-17

多轮对话与独立整理调用覆盖以下场景。通过指实际持久化结果、版本和随后回答均经核对，
不是仅凭协调者声称“已记住”；初次失败与后续修正分开记录。

| 场景 | 验证与结果 |
| --- | --- |
| 临时讨论 | 按钮右置、蓝色仍属未定实验；未写成长期偏好，后续整理也未提取这些选择 |
| 明确保存、纠正与部分撤回 | 同一 CLI 维护偏好保存后，改为“仅能稳定复现才先写复现”，再撤回语言约束；保持原 ID，版本从 1 到 3，验收前不得发布的条件保留 |
| 讨论后整理 | 先讨论默认依赖与诊断流程，主对话不调用写入；后来主动整理提取长期部分，保留已有人工记录 |
| 空闲更新 | 测试实例等待缩短到 1 秒；普通启动不联网合并到已有流程，再更新为运行时依赖需确认、开发测试工具可自行选择但须固定版本；同一自动条目从 1 到 3，未保留旧的笼统限制 |
| 已有内容压缩 | 两条相同记录、条目内各重复八次；归档副本并将保留项精简为一份完整约束，重点标识、原 ID、旧版历史保留 |
| 群内单次整理 | 修正后的实现对新群中两条各重复六次的记录，一次调用完成归档与压缩；离线、私人材料隔离、人工复核前不得发布三项条件完整，实例共享集合保持为空 |
| 冷启动 | 最新事实、条目版本、整理位置和开关恢复；真实模型按更新后的依赖区别回答，未沿用旧限制 |
| 隔离与界面 | 私人记忆未进入另一分身；应用内浏览器验证主动整理、即时等待、结果依据、开关保存；常规窗口与 390×844 检查，无水平溢出 |

模型选择记录为 [dsh-provider-qoder/dfmodel](https://github.com/mo-n/dsh-provider-qoder)。整理通过独立、无工具的宿主模型调用完成，
不会创建 Worker 或任务卡片。离线回归另验证群整理的输入只含群材料、非法来源与跨范围
提案被拒绝、并发编辑或新消息使旧结果失效、停止取消、失败不重复重试以及完整消息预算。

迭代中发现并修正：

- 真实模型正常结束使用 `stop`，最初误用 Agent 的 `completed` 契约，导致前台保存失败；
  保留空集合，修正终态适配后复测成功。
- 主动整理曾把“讨论期间暂缓写入”当成持续禁令。现输入真实触发阶段；手动操作可重新
  检查已有完整人类证据，但永久性“不记住”的要求仍有效。
- 模型曾复制裸记忆 ID 作为依据，初版只接受带前缀的引用；现展示专门的来源标识，并
  仅对当前可见集合中的裸 ID 做规范化，不接受陌生或其他范围的 ID。
- 初次去重归档成功，但保留项内部重复未被压缩。现由程序明确给出本次可编辑集合，
  避免把人工来源误解为主动整理也不能改；新增群案例在最终实现上单次通过。
- 主动整理原先依赖已加载聊天，现可只精简已有记忆，不创建会话；后台仍需完整聊天证据。
- 测试脚本曾把此前含“离线”的旧结果当作本次自动整理成功；改为同时检查新的整理时间、
  新条件和版本变化。新建实例未继承测试用短等待，也已单独设置后重测；不把旧结果计入通过。

这些合成场景验证的是机制和有限语义样本，不证明一般任务的提取准确率。重复文本压缩
尤其不是自然项目材料的压缩评测。后续真实应用开发的观察见下节；默认 15 分钟与字符预算
仍是可调整的工程起点。

## 真实应用开发：2026-11-17

从用户提供的候选中选择一个本地项目与证据管理应用。通过正常会话提出目标和验收标准，
由协调者自行选择技术栈与分工，再根据运行中的实际缺陷提供反馈；没有预先写好任务拆分，
也没有给整个任务设置 token 配额。所有测试模型固定为同一路由，插件保留默认 12000 字符
持久上下文预算与 15 分钟空闲等待。
长任务使用 0.15.0；发现的修订问题在 0.15.1 上完成针对性真实回放、冷启动及离线回归，
没有把针对性回放描述为完整应用任务的多次复跑。

工作涵盖真实 Web/API/CLI、SQLite、三个明确标记的虚构项目与 60 项演示任务、只读演示
Git、模板、导入导出、文件证据、依赖与验收历史，并分别在 Windows 与 WSL 运行。
演示任务数量不等于协调者派工次数。实现 Worker 连续接受补充反馈，期间经历三次宿主
原生上下文压缩；原生压缩不是把完整工作过程写进插件长期记忆。

人工独立验收发现并反馈了以下实际问题：

- 下游曾可在阻塞依赖尚未验收时通过；不存在的文件路径也曾被标成有效证据。修正后，
  八项独立领域契约覆盖依赖前置条件、无证据拒绝、失效传播、不自动恢复下游、重分配历史、
  版本冲突、依赖环与导入导出；本地文件增加存在性、允许根与内容核验。
- Windows 原生 Node 预检发现文件 URI 多出一层盘符；用真实 Windows 进程复测修正，
  没有把仅在 WSL 通过等同于 Windows 兼容。
- 应用内浏览器发现重复状态与关闭抽屉后焦点丢失；修正后在常规窗口和 390px 窄屏复查，
  关闭按钮与 Esc 都回到原任务，页面和抽屉无水平溢出。

这轮记忆观察围绕一条真正需要跨窗口沿用的项目环境背景，不把任务明细与每次测试数字
复制到长期记忆：

| 观察 | 结果与边界 |
| --- | --- |
| 环境从 WSL 改为 Windows 原生 Node | 同一 ID 与名称更新版本，当前集合只保留一条有效事实；旧值保留在版本历史 |
| 限定条件漂移 | 第二版把“不公开发布”扩成了“不推送或部署”；第一个无历史读者又传播了这个多出的限制，初次检查失败 |
| 数据纠正 | 正常发送澄清后，同一记录更新到第三版，明确允许本机启动和验收；这只证明测试数据被纠正，不能替代新代码复测 |
| 独立读者空闲 | 保留默认 15 分钟等待；只读读者在主任务仍工作时完成一次零修改整理，私人记忆保持为空，共享背景未被复制为新记录 |
| 主任务空闲 | 默认 15 分钟后，模型提出的新增项缺少合格的用户来源。程序拒绝整份提案，分身记忆仍为空，共享事实保留 |
| 下游产物回退 | 即使共享背景已正确，一份兼容文档仍写回旧的 WSL 主路径；作为验收缺陷单独修正，不能用记忆写入成功替代产物验收 |
| 修正后回放 | 重载宿主后，三个全新实例分别以原第一版背景和原环境变更原话做简化回放；均更新原 ID 到第二版，保留本地、单用户、无云与发布条件，未附加禁止部署。这不是完整重跑三次长任务，也不代表总体错误率 |
| 冷启动与纯上下文读者 | 当前事实、版本历史、整理位置与开关保留；全新读者零工具调用，七个环境／边界字段全部正确，私人及共享记忆均未改变 |

针对限定条件漂移，修订时不再把主对话生成的整段替换草稿交给整理模型；改用正式旧值与
当前用户原话生成新版。程序继续约束目标 ID、名称、范围与版本，首次新增仍可提供不受
信任的草稿。离线反例证明，即使调用方草稿附加未要求的禁止条款，该正文也不会进入更新
模型的输入。另修正总览规则工具的范围枚举：只展示总览实际支持的实例范围，后端原有
专属分身校验保持不变，避免模型先选择不支持的范围再重试。

0.15.2 在隔离宿主用正常会话回放来源错误，测试实例的空闲等待缩短为 2 秒。
测试在校验前将首次输出替换为仅引用助手消息的新增提案，随后由 Qoder 的 dfmodel
依据原证据和具体校验原因重新提案。最终两组回放各调用两次。已生效的发布约定保存为
一条事实，含双平台兼容验证和维护者验收条件，引用真实用户消息。明确为一次性的设置
未产生新记忆。已有人工记录和共享集合均保留。离线用例覆盖二次拒绝、游标保留和并发失效。

保留两项初次样本。模型曾将「先复述供核对」理解为约定尚未确认而选择零修改。一次混合样本
中，重试引用了有效用户消息，却在发布约定中附加验收记录留存要求与一次性样式的说明，
独立验收判为失败。来源校验验证消息资格和作用域，语义相关性仍由模型判断。

从提出目标到两项任务关闭约 110 分钟，由协调者派出一个实现 Worker 和一个独立复核
Worker，共 12 次补充指令。应用最终 WSL 套件 43 项通过，Windows 原生 42 项通过、
1 项浏览器测试按平台跳过；实际 Windows Edge 与应用内浏览器另覆盖展示和交互。
代码、文档与数据保留在本地，没有推送或公开发布。

长任务及随后交接／回放共观察到 620 条唯一原生助手消息，模型来源均为固定路由。
原生用量字段为：`inputTokens` 1,786,660，`cacheReadTokens` 104,918,272，
`outputTokens` 730,217，其中 `reasoningTokens` 342,613 为输出子项。
这些数值是该样本的观测量，不是预算、质量评分或总体调用费用。

这次自然任务检验的是长程执行、部分事实修订与验收反馈，不是大规模长期记忆准确率
评测。该任务没有自然产生超过默认记忆预算的大量有效事实；预算不足时的关键条件保留
仍由下面独立的压力场景支持。原生会话可观测用量不含独立整理调用，缓存读取是重复输入
流量，输出用量已包含推理子项，不能重复相加或把它们当成唯一历史长度。

## 既有事实与上下文选择：2026-11-14

| --- | --- | --- |
| 长程事实更新 | 作者连续 60 轮新增 44 条普通背景，并穿插日期、负责人和审核条件修订、只读讨论、归档与恢复；自动预算 3000 字符 | 稳定名称始终只有一条当前记录，修订替换旧值；长程过程中及最终共 9 次独立读者核对，每次六个当前事实／隐私字段均符合预期 |

| 最低预算与外部更新 | 自动预算 1000 字符，三个重点条目均放不下；两轮之间由操作者修改日期、负责人和审核条件 | 两轮均重新调用记忆读取，采用当轮新值；较长条目末尾的否定条件完整保留 |

原生会话审计确认隔离宿主的模型输出均来自指定路由；所检查的只读核对轮次没有记忆、
进展或约定写入，也没有派工。审计中的零运行错误不等于所有早期回答均正确，发现与
修正的问题列在下节。

## 对照与结论边界

对相同共享事实流做了一个受控对照：将按时间追加的事实文本取前 3000 字符，交给同模型
的普通新会话，不启用插件记忆，也不允许工具补查。四个关键字段中，对照正确 2 个，
新版完整条目选择正确 4 个。它说明此事实流中的前缀策略会漏掉后续修订与约束，
**不是旧版插件的完整端到端复跑，也不是多数据集统计结论**。

默认 12000 字符是可调整的工程起点；3000 和 1000 是压力测试设置，不证明任何一个
预算普遍最优。关键词相关性没有语义理解保证；不同名称下的矛盾事实仍需模型或用户
明确合并，不能把这些场景通过描述为一般长期记忆已被解决。

## 迭代中发现的问题

- 早期进展核对返回未知：当前问题还未进入选择逻辑，相关进展被普通记录挤出。
  对照原生宿主确认先组装、后 pre-step、再准入刷新的顺序；改为捕获当前认领的
  用户输入，动态内容在准入时重新选择，并补上相应接线回归。
- 宿主把时间和动态上下文也记为 user-role 消息；现按来源排除这些生成内容，避免它们
  覆盖用户问题或成为事实来源。新回归覆盖这两种原生消息形状。
- 复测曾复用相同结束标记，脚本误读上一轮答案；现每次请求生成唯一标记。原始失败
  记录保留，修复后的两次进展回答另行核对，没有用旧结果代替新请求。
- 初始评分把正确回答中提及的旧日期判为失败；最低预算评分也曾拒绝代码后附带的
  正确“未通过”说明。现核对结构化当前值和独立的能否发布字段，代码要求唯一且正确，
  不把历史解释或正确限定语当作事实错误。
- 空上下文的界面分支曾返回无法展开的值；修复后补上空列表回归，并复查真实页面。
